# ADR 0003: Adopt the Mirasim v2 authentication envelope

## Status

Accepted — 2026-09-01

## Context

Mirasim 0.0.260 replaced the relay's `mrs-sig-v1` request signature with a two-layer authentication envelope:

- `mrs-sig-v2` binds the device, client version, current bearer credential, semantic request metadata, and raw body.
- `mrs-seal-v1` encrypts the Mirasim signature and semantic metadata before a normal relay request leaves the client.

The device-session mint and ordinary relay requests deliberately use different envelopes. `POST /v1/device/session` is signed with the access token and sends its signature headers directly. Requests such as `/v1/messages`, `/v1/responses`, and `/v1/models` are signed with the device ticket, then move every `x-mirasim-*` header except `x-mirasim-client` into `x-mirasim-enc`.

Changing only `client-version` leaves a v1 client incompatible and results in the relay's `client_outdated` response. Bundling Mirasim's WebAssembly crypto core would duplicate an opaque runtime artifact and complicate native-plugin packaging, while all required primitives have standard Go implementations.

## Decision

1. Implement `mrs-sig-v2` directly in Go with Ed25519. Its canonical payload binds method, pathname, millisecond timestamp, nonce, device ID, client version, SHA-256 of the bearer credential, SHA-256 of sorted semantic metadata, and SHA-256 of the exact request body. An empty metadata set contributes a blank canonical line.
2. Keep the device-session mint unsealed. Sign it with the access token and send `x-mirasim-device`, `x-mirasim-ts`, `x-mirasim-nonce`, `x-mirasim-sig`, and `x-mirasim-client` directly.
3. For ordinary relay requests, generate a pooled `mirasim_<uuid>` session ID, a UUID per call, and an agent label selected from the wire route (`claude` for Messages and `codex` for Responses). Include these values in the v2 metadata hash.
4. Seal ordinary-request Mirasim headers with an ephemeral X25519 key, HKDF-SHA256 using the ephemeral public key as salt and `mrs-seal-v1` as info, and ChaCha20-Poly1305. Bind `mrs-seal-v1`, the uppercase method, and pathname as associated data.
5. Use the relay public key shipped by Mirasim 0.0.260 by default. Permit the same process-level `MIRASIM_SEAL_PUBKEY` override as the official client so a public-key rotation does not require storing secrets or changing auth records. Reject invalid keys and encryption failures instead of sending metadata in cleartext.
6. Strip every caller-supplied `x-mirasim-*` header before adding the plugin-controlled authentication envelope.
7. Keep fixed, non-secret test vectors generated by Mirasim's 0.0.260 crypto core. Test both exact signature bytes and exact sealed bytes, and independently decrypt integration-test requests.

## Consequences

The plugin now emits the authentication protocol expected by Mirasim 0.0.260. Merely rebuilding with the new default is not enough when an existing CLIProxyAPI config or auth record explicitly pins an older `client_version`; operators must update that explicit value to `0.0.260`.

Normal relay traffic exposes only the device ticket in `Authorization`, the public client version in `x-mirasim-client`, and the encrypted `x-mirasim-enc` value. Device signatures, session IDs, call IDs, and semantic metadata are no longer sent as plaintext headers.

The generated session ID is scoped to the pooled plugin client because the current Mirasim client boundary does not receive a stable downstream conversation identifier. Calls still receive independent UUIDs, and signature metadata remains deterministic after sorting.

The implementation depends on Go's HKDF and `golang.org/x/crypto` X25519/ChaCha20-Poly1305 primitives rather than Mirasim's WebAssembly module. A future upstream protocol version or relay-key rotation still requires fresh compatibility verification.

## Alternatives considered

- Keep `mrs-sig-v1` as a fallback: rejected because downgrade attempts would add extra authenticated traffic and the current relay explicitly requires the new client envelope.
- Embed and invoke Mirasim's WebAssembly crypto core: rejected because the native Go primitives match its fixed vectors without adding an opaque binary artifact or a WASM runtime dependency.
- Sign ordinary requests but leave the Mirasim headers unsealed: rejected because 0.0.260 removes those headers after creating `x-mirasim-enc` and refuses to send metadata in cleartext when sealing fails.
- Omit session, agent, and call metadata: rejected because the official client includes them in both the signature and encrypted envelope, and generating equivalent non-secret identifiers is inexpensive.
